# How Sable Works

## Overview

To set the stage for talking about how **Sable** works, let's first talk about how things works without **Sable**.
Without **Sable**, you'd just use the [Marten Command Line Tooling](https://martendb.io/configuration/cli.html#command-line-tooling) support to run commands like `marten-patch` and `marten-apply` on your project.
**Sable** does not add any additional functionality to that toolset. In fact, it is built on top of it, and will literally just run those same commands that you'd run manually.

When manually using the command line tooling support, you need to connect to an actual database, which introduces the problems outlined in [Why Sable](../introduction/why-sable).
**Sable** solves those problems by using a temporary shadow database instead of an actual one. For instance, when running the **Sable** command to create a new migration, **Sable** will:
- Dynamically create a Postgres docker container to be used as the shadow database.
- Create a script from the existing migrations.
- Apply the script to build the shadow database.
- Run the `marten-patch` command on your project. That command is executed in a context where an environment variable is set by Sable. That environment variable is
then used to override the connection string for Marten in the project so that it points to the Docker container instead of an actual database. The script generated by Marten
is then saved in a sable `migrations` directory. If no changes were detected, the file fill be empty.
- Delete the Docker container.

## Custom Shadow Database

By default, **Sable** uses a Docker container built from a version of  the official [Postgres](https://hub.docker.com/_/postgres) image from the DockerHub registry.
However, in a corporate environment, maybe you have to use an image from an internal private registry. Or maybe you just want to use a different image from DockerHub.
That's possible. Any **Sable** command that needs to use a shadow database has a `-c|--container-options` option. That option can be used to point to a JSON file that contains
the configuration for how build a custom container for the shadow database. An example looks like this:
```json
{
  "Image": "postgres:15.1",
  "PortBindings": [
    {
      "HostPort": 5470,
      "ContainerPort": 5432
    }
  ],
  "EnvironmentVariables": {
    "PGPORT": "5432",
    "POSTGRES_DB": "postgres",
    "POSTGRES_USER": "postgres",
    "POSTGRES_PASSWORD": "postgres"
    
  },
  "ConnectionString": "Host=localhost;Port=5470;Username=postgres;Password=postgres;Database=postgres"
}
```

`ConnectionString` is the connection string that should be used to connect to the container once it is running.

## Migration Tracking and Idempotency

Sable maintains `<database-schema-name>.__sable_migrations` to track applied migrations. By default, each migration is placed in a tagged `$sable$` guard and an outer transaction:

```sql
BEGIN;

DO $sable$
BEGIN
    IF NOT EXISTS (
        SELECT 1
        FROM orders.__sable_migrations
        WHERE migration_id = '20231013224735_AddIndexOnCustomerId'
    ) THEN
        CREATE INDEX mt_doc_order_idx_customer_id
            ON orders.mt_doc_order USING btree ((CAST(data ->> 'CustomerId' as uuid)));

        INSERT INTO orders.__sable_migrations (migration_id, backfilled)
        VALUES ('20231013224735_AddIndexOnCustomerId', '0');
    END IF;
END
$sable$;

COMMIT;
```

If the history record already exists, the guarded DDL and history insertion do not run again. Otherwise, the DDL and history insertion succeed or fail in the same transaction. The tagged `$sable$` delimiter also prevents a Marten function body using `$$` from terminating Sable's guard.

## Safe Top-Level Schema Preambles

Some Marten migrations begin with a top-level `DO` statement that idempotently creates the configured database schema. PostgreSQL does not allow Sable to nest that statement inside another PL/pgSQL `DO` block. Sable recognizes the bounded schema-creation shape, preserves it unchanged at the top level, and guards the remaining DDL and history insertion:

```sql
BEGIN;

DO $schema$
BEGIN
    BEGIN
        EXECUTE 'CREATE SCHEMA IF NOT EXISTS orders';
    EXCEPTION
        WHEN duplicate_schema THEN NULL;
        WHEN unique_violation THEN NULL;
    END;
END
$schema$;

DO $sable$
BEGIN
    IF NOT EXISTS (
        SELECT 1
        FROM orders.__sable_migrations
        WHERE migration_id = '20260710000001_AddOrderFunction'
    ) THEN
        CREATE OR REPLACE FUNCTION orders.answer() RETURNS integer
        LANGUAGE sql
        AS $$ SELECT 42; $$;

        INSERT INTO orders.__sable_migrations (migration_id, backfilled)
        VALUES ('20260710000001_AddOrderFunction', '0');
    END IF;
END
$sable$;

COMMIT;
```

One or more consecutive recognized schema preambles can appear before the guard. They run on each replay because their only accepted effect is idempotent creation of the configured schema. Sable does not suppress schema creation for externally managed schemas, and this behavior is not general support for hoisting arbitrary `DO` statements.

### Catalog-guarded producer output

Newer Weasel output adds an existence check around the exception-protected operation:

```sql
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_catalog.pg_namespace WHERE nspname = 'orders') THEN
        BEGIN
            EXECUTE 'CREATE SCHEMA IF NOT EXISTS orders';
        EXCEPTION
            WHEN duplicate_schema THEN NULL;
            WHEN unique_violation THEN NULL;
        END;
    END IF;
END
$$;
```

Sable preserves this entire recognized preamble unchanged before its `$sable$` history guard; remaining product DDL and history insertion stay inside that guard. The catalog check avoids an unnecessary database-level `CREATE` privilege check when the schema already exists. The `duplicate_schema` and `unique_violation` handlers protect a concurrent creation after the check. Removing either protection or rewriting this into the older exception-only form is not an equivalent fix.

The catalog literal is an exact schema-name value, not an SQL identifier. For example, a configured `"Orders"` and dynamic `CREATE SCHEMA IF NOT EXISTS "Orders"` require catalog value `'Orders'`, not `'orders'` or `'"Orders"'`. Unquoted identifiers follow PostgreSQL folding; quoted case and each literal/identifier escaping layer are preserved. Unrepresentable values such as NUL remain rejected. PostgreSQL's own identifier truncation and `name`-type comparison rules still apply at execution; Sable does not impose an additional schema-name length limit.

This is not general conditional SQL support: aliases, broadened predicates, additional operations, or missing/extra/side-effecting handlers remain unsupported. Both approved handler orders, supported dollar tags, well-formed comments, and insignificant whitespace/casing are accepted. The outer `DO` statement terminator remains required. Older exception-only and information-schema histories retain their existing behavior; mixed consecutive recognized preambles are supported, but an unsupported following `DO` rejects the composition as a whole.

A restricted role still needs schema/object/history privileges and cannot create a genuinely missing schema without database `CREATE`. An infrastructure migration that unconditionally executes `CREATE SCHEMA IF NOT EXISTS` can also require that privilege even for an existing schema. This recognition change does not alter bootstrap policy, grants, migration history, or transaction directives. Do not rewrite historical SQL, increase grants, or disable idempotence just to bypass recognition.

When idempotence wrapping is enabled, an unsupported or malformed leading `DO` fails before script output or database execution with exit code `1`; an existing requested output is preserved:

```text
Sable cannot safely wrap migration '<migration-id>' because it begins with an unsupported top-level DO statement. Only a recognized safe schema-creation preamble can be moved outside the idempotence guard. Use Sable's no-idempotence workflow only when the migration is independently idempotent.
```

The [Schema Preamble Compatibility Sample](https://github.com/bloomberg/sable/tree/main/samples/Sable.Samples.SchemaPreamble) contains authentic generated Marten SQL and commands for Docker-free composition, disposable PostgreSQL replay, and a full temporary-copy `migrations add` check. It preserves the older Marten 9.8.1 producer fixture. The separate [Catalog-Guarded Schema Preamble Sample](https://github.com/gabrewer/sable/tree/main/samples/Sable.Samples.CatalogGuardedSchemaPreamble) pins Marten 9.50.3 with resolved Weasel 9.45.0 and includes authentic guarded output. Its verification covers CLI-driven double replay, an independently verified restricted role, missing-schema rejection, complete temporary-copy generation and fresh replay, and an isolated locally packaged CLI. Sample pending-mapping variables are repository test seams, not Sable configuration. All database verification uses explicitly owned local disposable targets; generated SQL is applied through Sable, never manually.

## Advanced Wrapper Directives

`-- Sable NoTransactionWrapper` removes only Sable's outer `BEGIN` and `COMMIT`; the migration-history guard remains enabled.

`-- Sable NoIdempotenceWrapper` is authoritative. Sable does not split, hoist, or classify the migration's top-level SQL. The original migration remains top-level, followed by Sable's existing conditional history insertion. Use this directive only when every source statement is independently idempotent, such as `CREATE INDEX CONCURRENTLY IF NOT EXISTS ...`.
